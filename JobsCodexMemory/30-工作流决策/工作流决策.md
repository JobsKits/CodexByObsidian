## 五、Jobs 二次封装 API 的过期兼容

- 来源：用户于 2026-07-20 明确确认。上层使用 Jobs 自建 Pod / DSL 二次封装 API 时，不应因底层 Apple API 过期而继续看到系统 deprecated 警告。
- 新 API、旧系统回退和必要的最小范围压警告由封装实现内部统一处理；调用方不再补 `@available` / `#available` 分支或直接调用裸系统 API。
- 该决策同时适用于 Swift 工程、OC 新工程和 OC 老工程，并持续写入 `jobs-swift` / `jobs-objective-c-pods` Skills。只有 Jobs API 本身被废弃且有 Jobs 替代入口时，才允许对外标记 deprecated。

## 六、Jobs DSL 链式返回类型

- 来源：2026-07-24 多次 OC / Swift 编译修复交叉验证，并与 Jobs 全局 DSL 规则一致。链式方法必须返回可继续调用的当前具体对象；除明确终止动作外，不写只执行副作用却返回 `void` 的 DSL。
- 子类专属 DSL 必须在可能把静态返回类型降为父类的通用 DSL 之前调用；例如 `CAShapeLayer`、`UIButton`、`UITableViewCell` 的专属配置不能接在返回 `CALayer` / `UIView` 的链后。无法保持具体类型时拆分为独立调用，不用强制类型转换掩盖 API 设计问题。
- 新增或修改 Jobs DSL 时同时检查 Swift、OC 新工程和 OC 老工程的对应调用；编译验证要覆盖真实工程模块，避免只做文本扫描后遗漏链式类型错误。

- API 真实签名和语义以 Jobs 自维护源码与公开入口为唯一权威；README、工程配置文档和 CodeSnippets 只做消费说明，不得反向定义 API。

## 八、Jobs DSL“一镜到底”整改门禁

- 来源：用户于 2026-08-03 明确确认。Swift、OC 新工程与 OC 老工程的 Jobs 自维护代码统一执行“一镜到底”：同一配置语义的主对象只起链一次，子对象通过宿主级 DSL 或配置闭包继续收口。
- 批量整改必须先按文件头、版权或明确接管信息确认 Jobs 所有权，再用审计脚本识别裸属性赋值和重复起链；外部 Pods、手工第三方、供应商、生成代码与所有权不明确文件固定排除。
- 自动迁移只能处理类型与语义明确的 Jobs DSL；出现同名异类型 API、值类型 mutating 链或静态类型降级时，必须补真实归属层 API 或人工收口，并以真实 workspace 构建纠错。迁移脚本复跑应为 0 改动，相关 README、Demo、工程文档、CodeSnippets 与 Skills 同步更新。

## 九、Git 仓库 `work/` 生成目录忽略

- 来源：用户于 2026-08-12 明确确认。Git 仓库中名为 `work/` 的目录默认视为本地中间产物或生成产物，使用仓库自身 `.gitignore` 中的 `work/` 规则排除，不提交进 Git。
- 批量扫描时按真实仓库根目录去重，区分已忽略、未跟踪和已跟踪三种状态。`.gitignore` 不会自动停止跟踪已入库文件；若 `work/` 已被跟踪，必须先确认其中没有应保留的源码或资产，再只从 Git 索引移除，不删除本地文件。

## 十、OC 新旧工程默认同步门禁

- 来源：用户于 2026-08-12 明确确认。OC 新工程与 OC 老工程只允许存在本地 Pod 集中管理和主工程直接集成这一种架构差异；对应 Jobs 自维护功能的源码、API、Demo、资源、行为和文档必须保持一致。
- 用户只要求修改一侧时，默认在同一任务同步另一侧，不等待用户再次提醒。开始前建立本地 Pod 路径与老工程主工程路径的映射，结束前对两侧做归一化差异检查。
- 新工程保留 podspec、Podfile、本地 Pod 聚合头和 Development Pods 装配；老工程改为源码 / 资源落入主工程并维护 Xcode 引用、Build Phases 与 target membership。不能为追求文件形态一致而给老工程新增 Pod，也不能把集成形态差异扩大成功能差异。
- 第三方、生成代码和明确的语言边界继续遵守所有权规则；确实没有对应项时必须检索后报告“无需修改”。该门禁由 `jobs-objective-c-pods` Skill 持续执行。

## 十二、Shell 依赖链完整性与条件式自愈

- 来源：用户于 2026-09-13 明确确认。脚本为了使用一个目标工具时，必须先建立该执行路径的完整依赖链或依赖图；不能只判断末端命令是否存在，还要验证本次安装、升级、同步或修复真实依赖的每一层是否可用。
- 每层采用“发现、健康检查、条件式安装或修复、刷新当前会话、二次复检”的闭环。只沿缺失或损坏分支向上溯源，复用健康依赖和等价来源；修复后仍不可用时停止下游业务并明确报告失败层级，不无限重试、不带病继续。
- 完整依赖链自检不扩张执行权限；只读检查可自动执行，安装、升级和修复仍必须属于用户明确请求或入口已清楚声明的行为。该决策由 `jobs-macos-shell` Skill 持续执行。
