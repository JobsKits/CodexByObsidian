## 二、<span id="download-rate-limits">附件传输与限流恢复</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- <span id="asset-unattended-retry">附件传输与校验持续自动重试</span>：来源：用户于 2026-11-09 提供第 6 片因 curl 28 超时、尝试六次后停止且后 163 片未尝试的日志，并明确要求失败后一直尝试，不能达到六次便退出；日志事实 observed，需求 confirmed，仅适用于当前 Release 下载入口。附件传输及校验不设重试次数或总时长上限，无需再次确认；保留断点持续处理当前附件，成功后自动继续后续附件，直到完成或用户主动取消。实现 scoped-verified，具体本地错误与保护边界见下文。
- 普通失败按 1→2→4→8→…→300 秒退避，后续保持 300 秒；HTTP 401／403／404／429／503 从 60 秒开始，按 60→120→240→300 秒退避。优先遵守更长的 `Retry-After`（秒数／HTTP 日期）或配额恢复时间；零值、过期时间回退为正数，避免空转。HTTP 拒绝同样持续等待重试，恢复可能需要远端权限或附件问题被处理，不以重试绕过认证。
- curl 返回 0 但文件未达到声明大小时继续续传；坏摘要、超长断点、curl 33 或 HTTP 416 触发重新获取。首份问题断点保存在同版 `.partial/<ID>.part.rejected.XXXXXX/` 中供核对；同一次运行的后续失败只重置本轮重新获取的候选文件，不无限生成备份，不覆盖正式完成文件。
- 本地写入／配置错误、正式同名文件校验冲突、附件身份变化和不安全路径仍真实报错并保护已有数据；不绕过证书或认证校验，不切换来源、镜像或代理。`Ctrl+C` 退出 130、关闭终端的 HUP 退出 129，保留已完成文件及断点；传输和等待中的取消不能被重试循环吞掉，未全部校验成功不进入合并。
- 已替代（superseded，2026-11-09）：旧“每片最多尝试六次；持续网络失败或无恢复依据的 403 停止整个下载队列”行为被[附件持续自动重试](#asset-unattended-retry)替代。下方旧版停止队列、404 停止等验证记录保留为历史范围，不能作为本轮持续重试已通过的依据；本要求不改写其它脚本或 SDK 获取的既有规则。
- 同日用户补充“确认仓库后清单第一步 403 退出”；实测响应头 `x-ratelimit-remaining: 0`，恢复时间为 2026-11-07 08:41:28（北京时间），本次配额耗尽事实 confirmed。初版恢复面板要求用户选择等待，该限流交互现已被下述自动等待要求替代（superseded）；非限流错误仍保留本地记录／重试／返回入口。
- <span id="api-unattended-wait">API 限流默认自动等待</span>：来源为用户同日明确要求省心无人操作、可关窗后自行重启或保持窗口等待；需求 confirmed，适用范围仅当前 Release 下载入口。明确 429、或 403 且配额为零／有等待头时，在 `fetch_api` 内原地等待并重新请求同一分页，不再弹菜单要求确认；直到恢复或用户取消，不设该限流等待的次数上限。保留已取得的前页，不从第 1 页重抓；服务器有效等待时间优先，缺失／过期时间按 60→120→240→300 秒退避，最高保持 300 秒，避免零等待循环。
- API 清单自动等待显示预计再次请求时刻及剩余分秒，每分钟更新；按真实截止时间每不超过 30 秒检查，电脑睡醒后重新核对。`Ctrl+C` 走退出 130，关闭终端显式处理 HUP 走退出 129，保留完成文件及断点并清理本轮临时文件／锁。API 清单阶段的本地写入、证书、无证据的 403、404 和坏 JSON 不当作明确限流无限等待；`--list` 只读查询仍直接失败，不自动长期阻塞。
- 本地历史计划只读恢复真实子仓 `Releases/<标签>/.partial/*.json`，不伪造 Release ID，也不将旧记录当作当前线上清单；校验路径／链接、规范身份 JSON、ID／名字唯一性、同仓同版本官方 URL、摘要与完整卷号后才发布清单。无有效记录回恢复面板，附件可返回本地版本，本地版本可返回恢复面板；在线分页未全部成功时不发布前几页结果。

## 三、<span id="download-locks">下载锁与异常退出</span> <a href="#前言" style="font-size:17px; color:green;"><b>🔼</b></a> <a href="#🔚" style="font-size:17px; color:green;"><b>🔽</b></a>

- 来源：用户同日提供 09:08 运行日志，线上清单与完整分卷计划已正常，最终被旧 `.download-lock` 空目录阻止；事实 observed。只读核验未发现相关业务脚本／curl 或文件占用，复核 inode 与空目录后已精确移除该旧锁，未修改分卷或断点；实际版本目录新锁获取、释放、再次获取通过。
- 已查明 zsh 函数中注册的 `EXIT` 在该函数返回时触发，旧 `initialize_runtime` 因此提前执行空锁清理，无法负责后续真正退出；现在使用全局 `TRAPEXIT()` 保留原退出码，子 Shell 不清理父进程持锁。新近注入的终端配色和提示渲染保持不变。
- 当前使用 macOS 自带 `zsh/system` 的 `zsystem flock` 系统文件锁，`.download-lock` 为长期保留的普通空文件，不 unlink／替换以保持同一锁域；持有进程结束时内核释放，文件存在本身不是忙锁判断。旧目录、符号链接及含未知内容对象保守拒绝；不按年龄抢占，不终止其它下载。
- 取得系统锁后检查目标 `.partial` 的遗留 curl 与文件占用，防止只强杀父脚本后孤儿传输仍写入。发现占用或无法核验时释放本轮锁并停止，不重复写同一断点；正常释放只关闭本进程锁 FD。
